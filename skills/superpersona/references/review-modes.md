# Fast, Deep and native execution

Review depth is separate from evidence mode (concept, design, interactive, implementation) and execution method (native workers, sequential simulation, external engine).

| Requested mode | Inferred size | Required work | Output |
|---|---|---|---|
| Fast / 快速 | Normally 2–3 personas, 1 loop | Primary job, main journey and highest-relevance recovery branch; compact synthesis | Selected panel, scope, supported findings, important unknowns, prioritized next actions; include all serious supported findings |
| Deep / 深入 | Normally 4–7 personas, maximum 3 loops; fewer if sufficient | Value/logic, journey/recovery, then evidence challenge using the existing three-loop contract | Full report contract, coverage matrix, stable findings and challenge dispositions |
| Auto / omitted | Use task-based sizing in SKILL.md, including the existing 2-loop middle tier | Smallest useful coverage based on actual roles, branches and requested depth | Explain choice and begin; no missing-mode or missing-count gate |

Examples: `$superpersona fast` or `$superpersona deep` with the target supplied in context. Natural-language equivalents work too. Exact numeric counts and explicit budgets override mode defaults. “Fast, 4 personas, exactly 2 loops” means four personas and two purposeful loops with concise output. “Deep, 2 personas, 1 loop” keeps the limits and reports omitted depth. Preserve the established named presets in SKILL.md; Fast is a flexible depth mode, not a rename of the fixed Quick preset. Use the report contract’s compact Fast rendering; full cards and matrices remain working evidence unless useful to show. Do not infer a guaranteed duration or token price from the mode label.

## Use the calling runtime

Both modes use the current assistant and whatever authorized worker tools its runtime exposes. Honor model choices where supported; do not claim every worker inherits an identical model or subscription entitlement. No separate model API setup is required for the native skill workflow. If worker tools are unavailable, perform separate sequential passes and disclose the limitation. Count worker launches separately from personas and completed passes.

## Optional interaction scenario in Deep

Use only when relationships materially affect the decision, such as a buyer/seller dispute or a member/admin handoff. Fit it inside the selected loops and budget, normally the journey/recovery loop:

1. Preserve independent first-pass findings before introducing any interaction.
2. Define the scenario, starting facts, each actor's visible information and allowed actions. Keep private knowledge and permissions separate.
3. Bound the exchange (normally one action and one response per involved persona), recording the action, visible response and changed state.
4. Compare the resulting handoff or disagreement with stated product rules. Preserve unresolved tradeoffs. The third loop can challenge the interpretation.

This is an agent-based scenario rehearsal, not actual product execution, independent fresh-user evidence, market forecasting or a MiroFish engine run. Do not change persona expertise merely because the reviewer has learned previous findings.

## External-engine boundary

This student edition includes native reviews only. External engines, installers,
provider configuration and API credentials are not included. A native simulation
must never be presented as an external-engine run or real user research.
