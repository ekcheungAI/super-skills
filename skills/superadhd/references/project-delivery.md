# Fit the deliverable to the project

Use this reference for non-engineering or mixed work when output shape or
completion evidence needs thought. Start with what the user needs to receive,
not a domain checklist. Use the team's existing format when known. None of the
examples below authorizes implementation, publication, bookings, spending,
external assignment, or saving personal notes beyond the requested scope.

## Select only useful fields

| Work | Useful output | Proportionate evidence of completion |
|---|---|---|
| Writing, video, design | Creative brief, outline, script, or requested artifact; audience, message, channel and supplied assets | Fidelity to source facts, audience, tone, format and constraints; an annotated sample can resolve subjective quality |
| Research or business decision | Decision question, evidence comparison, tradeoffs and recommendation | Sources actually support claims; facts, interpretations and unknowns are distinct; recommendation answers the decision |
| Events or operations | Run of show, operating procedure, responsibilities and dependencies | Critical steps have inputs, a proposed or confirmed owner, and a checkable handoff; contingencies only for material failure points |
| Teaching or learning | Learning outcome, lesson sequence, practice or assessment | Learner can demonstrate the intended skill in an exercise; a slide deck alone does not prove learning |
| Personal planning | Current focus, a startable next action, waiting items and retained ideas | Plan respects stated commitments and available capacity; do not manufacture a productivity target or turn reflection into homework |
| Product or engineering | Lightweight task or PM/CTO brief via the dedicated reference | Observable behavior, justified discovery and relevant verification; no invented architecture or performance baseline |

These are examples, not an exhaustive classifier. For another domain, use the
same outcome/recipient/deliverable/constraints/evidence reasoning. Apply the
relevant specialist's domain standards without adding unrelated procedures.
Research that finds insufficient evidence can still be complete if its limits
and the next discriminating check are clear. A recommendation is not a user
decision; simulated feedback is not audience research.

For subjective work, prefer a real reference, a small contrast, or an annotated
sample to an invented quality score. For learning, content completion and
observed learning are separate claims. For operations, proposed roles are not
accepted assignments. For personal plans, suggested time blocks are not booked
calendar events.

## Examples that change the next action

### Creative output now

Input: "幫我理順同寫埋：60 秒廣東話短片，教新手用 AI 整理會議筆記，唔要
賣廣告口吻，最後叫佢試一次。"

Deliver the script directly using those constraints. No PM brief or mandatory
question is needed. If a tool is unspecified, keep the script tool-neutral;
do not invent product features or claim the video has been produced/published.

### Research with an undecided preference

Input: "I have notes for three newsletter tools. Help me decide; I don't know
which feature matters most."

Use the supplied notes to identify the actual tradeoff and separate unsupported
claims. Offer a short comparison or a concrete usage scenario if needed. Do not
ask the user to rank a long feature list or quietly assume the biggest platform
is best. Respect a request to use only those notes; otherwise verify material,
changeable facts with authorized research before relying on them.

### Operations with a fixed deadline

Input: "Friday workshop: room confirmed, slides unfinished, supplier hasn't
confirmed microphones. Just organize the remaining work."

Separate slide preparation from the supplier dependency. Identify the next
useful decision or a proposed fallback if audio is essential. Produce the
remaining-work brief; do not message the supplier or assume somebody accepted
an assignment. Do not invent headcount, budget, or a new delivery date.

### Teaching plus promotion plus software

Input: "我想做個 AI 課程，又想拍片宣傳，網站報名好似有問題，但未諗好教乜。"

Reflect three streams: course learning outcome, promotional content, and reported
registration trouble. Promotion depends on course positioning; registration
investigation can be independent once target and execution scope are known.
A useful first question is: "你最想學員上完堂做到邊件事？" Do not treat the website
report as authority to edit it or automatically make it the first priority.
If the user also requests investigation of a known site, perform authorized
independent checks while the learning outcome remains open.

### Personal planning and later resumption

Input: "Client proposal due today; course idea can wait. I only have 20 minutes.
Help me get started, don't plan the whole week."

Recommend a startable proposal step within the stated constraint, keep the
course idea tentative, and avoid a weekly schedule. When the user returns,
briefly restore the active goal, latest decision and next action from available
context; ask about changes only if material. Do not claim to remember unavailable
context or save the raw conversation automatically.

## Preserve clarity through changes

When switching recipients or domains, update the deliverable and its completion
evidence together. "Actually this is for learners, not the CTO" changes both
language and format, not just the title of a technical brief. Preserve still-valid
constraints and retire conflicting ones. If the user changes the objective,
make that change explicit; otherwise answer a side question and resume the
existing objective. Keep raw personal detail out of professional handoffs unless
it is necessary and authorized.
